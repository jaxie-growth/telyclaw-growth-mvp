# TelyClaw Growth Engine

> **Real-time Social Trend → Content Growth Engine**
> TelyClaw Growth Lead · Vibe Coding Challenge 交付物

一个可运行的 MVP：持续监控 X（Twitter）上的财经类账号 → 自动识别正在加速的热点话题 → 用可解释的 **Opportunity Score** 排出"最值得 TelyClaw 跟进"的机会 → 生成 3 个角度的内容草稿（含至少 1 条可直接发布的推文）→ 人工审核后发布，并把每一次动作沉淀成增长指标。

核心工作流：`Monitor → Detect → Rank → Ideate → Craft → Review → Publish`

## 2. 产品逻辑（Product Logic）

**要解决的问题**：TelyClaw 的产品是"AI-native 的社交增长引擎"。作为增长负责人，最大的浪费不是不会写内容，而是**热点窗口期太短**——一个话题从起量到被所有人写完通常只有几小时，而人工"看盘 → 判断 → 找角度 → 写草稿 → 审核"的链路根本跟不上。

**这个 MVP 的解法**：把"热点捕捉"变成一条有 SLA 的流水线，并让机器只做机器擅长的事（监控、聚类、打分、起稿、自评），把判断权完整留给人（编辑、批准、发布）。

| 环节 | 机器做什么 | 人做什么 |
|---|---|---|
| Monitor | 拉取配置账号在指定时间窗口内的帖子；**排期监控可无人值守定时轮询** | 决定盯谁、盯多久、要不要开自动轮询 |
| Detect | 聚类成话题、自动命名、生成摘要、**双口径判断是否在加速/起爆** | 判断这个热点是否可信 |
| Rank | 按 7 个因子算 Opportunity Score 并给出理由 + **时效建议** | 调整权重（=定义什么算"值得"） |
| Ideate / Craft | 生成 3 个角度 + 至少 1 条可直接发布推文 + **编辑 Agent 自评** | 编辑、改写 |
| Review / Publish | 原创度校验、状态流转、**角色权限校验** | 内容编辑改写 → 审核人批准 → 发布人发布 |

### 2.1 界面设计（UI Design System）

前端仍是零依赖原生 JS（无构建、无框架），但视觉层按一套设计令牌重写过，目标是"高级、简洁、大气、易操作"：

| 做法 | 说明 |
|---|---|
| **设计令牌统一** | 颜色 / 圆角 / 阴影 / 间距全部收敛到 `:root` CSS 变量（`--accent`、`--r-lg`、`--sh-2`…），换主题只改变量 |
| **粘性导航** | 顶栏 + 页签合并为一个 sticky appbar，任何位置都能切页签、切身份、看提醒 |
| **页签带图标与徽标** | 账号 / 热点 / 草稿 / 发布数量直接显示在页签上，一眼看出各环节存量 |
| **数字等宽** | 所有指标用 `font-variant-numeric: tabular-nums`，表格与卡片对齐 |
| **「下一步建议」条** | 概览页按当前状态给出唯一建议动作（没抓取→抓取、有热点没草稿→生成、有草稿→审核…），一键直达 |
| **流程步骤条** | 7 步闭环带序号圆点，完成的环节自动点亮 |
| **深链路由** | 页签写入 URL hash（如 `#ranking`），刷新不丢上下文，也可直接把某一页发给别人 |
| **键盘快捷键** | `1`–`8` 切页签、`R` 跑流水线、`G` 生成、`T` 演示、`?` 看帮助、`Esc` 关演示 |
| **空状态与图标** | 每个列表都有明确的空状态插画式提示；图标全部内联 SVG（无额外请求） |
| **可访问性** | `:focus-visible` 焦点环、`prefers-reduced-motion` 降级、按钮 `title` 说明权限原因 |

**一句话**：这不是一个 Twitter 监控工具，而是一套把实时趋势转成内容增长机会的闭环系统。

## 4. 数据获取方案（现实约束与生产化路径）

题目允许"如果无法直接获取完整实时数据，可以使用合理的替代方案完成 MVP"，并要求在 README 中说明真实生产会怎么解决。

**当前 MVP：`DATA_SOURCE=simulated`**

- 内置一份**确定性仿真数据集**（`src/dataset.js`）：14 个财经类账号、最近 7 天约 700 条帖子，由 11 个"话题种子"驱动生成，带真实趋势形状：
  - `phase[7]`：话题 7 天活跃度曲线（有的升温、有的衰减）；
  - `burst`：新闻爆发窗口（比如 CPI 公布后 6–11 小时集中刷屏）；
  - 同话题帖子共享锚点实体与主标的，因此**聚类、打分、排序的每一步都能被验证**，而不是对着随机噪声调参。
- 优点：无需任何 key、离线可跑、结果可复现（同一分钟内多次抓取结果一致），面试演示不会因为额度/限流翻车。

**生产环境（已预埋适配层 `src/ingest.js`）**

按"先能跑，再跑好"分三个阶段，而不是一步到位上官方 API：

**阶段 0 · 冷启动：账号池方案**（0–3 个月，成本最低）
不等官方 API 审批额度，先用**多账号轮换**拿到真实数据：

- **账号池**：维护一组授权账号，随机/轮流调用 X 的 Search 与 GraphQL 端点，单账号触发限流就自动换下一个；
- **会话与代理**：会话持久化到本地库，每个账号绑定独立出口代理，避免同 IP 批量行为被关联；
- **并发与退避**：异步并发 + 指数退避重试，把配额摊平到整个轮询周期。
- 业界已有成熟实现可直接借鉴（如 `twscrape`：账号池 + SQLite 会话 + 限流自动切换 + 每账号代理，见 §17）。

**阶段 1 · 稳态：官方 X API v2**
`DATA_SOURCE=x_api` + `X_BEARER_TOKEN`，走 `GET /2/users/by/username` + `GET /2/users/:id/tweets`，已实现字段映射（含 `public_metrics` → 互动量加权）。限制：免费档几乎不可用，Basic/Pro 档有月读量与 QPS 限制，因此必须做配额管理。**为什么要从阶段 0 过渡到阶段 1**：账号池方案稳定性和合规性都不如官方通道，它是"冷启动的桥"，不是终局。

**阶段 2 · 配额与成本控制**（真正上生产必须做的三件事）：

- **账号分层**：核心账号（10–20 个）走官方 API 高频拉取；长尾账号走批量端点/日更，降低成本；
- **增量游标**：本地保存 `since_id` / `last_seen_at`，只拉新内容，避免重复计费；
- **降级链**：官方 API 限流 → 第三方聚合源（RSS / 授权数据商）→ 最近一次快照（标记 stale 并在 UI 提示"数据可能滞后"）。

**实时性**：需要近实时时用 X 的 filtered stream（付费档）+ 本地队列削峰；否则 5–15 分钟轮询就足够捕捉"小时级窗口"。

**合规边界（这一条必须讲清楚，不能含糊）**：

- 只读**公开**数据，遵守平台 ToS 与 robots 规则；
- 账号池方案在 X 的 ToS 里属于**灰色地带**——`twscrape` 自己的 README 都写明"X 的 ToS 不鼓励多账号，请自行评估"。所以定位只能是**冷启动过渡**，且必须限制请求频率、不做数据二次分发；
- 拿到官方额度后应尽快切到官方通道，把账号池降级为兜底；
- **发布动作永远走官方 API 且必须有人审批，不做全自动发帖**（本 MVP 的发布也是模拟的，见 §11）。

## 5. 热点识别逻辑（Trend Detection Logic）

回答的问题是：**"我监控的这群人，现在主要在讨论什么？哪些话题在快速升温？"**

1. **清洗与分词**（`tokenize`）：cashtag（`$NVDA`）权重 ×2.5、2 字母术语白名单（ai/bp/etf…）、英文停用词过滤；同时抽数字事实（`+2.4%`、`$70bn`、`25bp`）。
2. **聚类**（`clusterPosts`）：帖子按互动量降序作为"簇心候选"，与已有簇做 **加权 Jaccard + 重叠系数的混合相似度**（`0.5 × Jaccard + 0.5 × 重叠系数`）——单一 Jaccard 对"长短帖差异"太敏感，混合口径同时看"整体有多像"和"较小的集合被包含多少"。相似度 ≥ 0.26 并入该簇，最后再做一轮簇间合并（≥ 0.30）。
3. **同类合并**（`mergeBySeed`）：词面聚类会把同一话题的不同侧面拆成多个小簇（Fed 的"dot plot 党"和"duration 党"）。用主题词典对齐后按主题 id 合并，避免排序里出现 5 个"Fed 热点"互相打架。
4. **自动命名**（`nameCluster`）：对簇内词做 **IDF 加权**（在整份语料里到处都出现的 `desk` / `chatter` 没有区分度，会被压下去），取 top 词生成名字；若与主题词典命中率高，则使用可读的主题名（`Fed / rate-cut repricing`）。
5. **趋势量化（双口径，这是排序质量的关键）**：单一指标一定会出错，所以同时算两条互补的口径：

   | 口径 | 算法 | 回答的问题 | 单独使用时的盲区 |
   |---|---|---|---|
   | **A. `growth`（环比）** | 窗口对半切，比较前后两半的**每小时发帖速率** | 趋势**形状**：在升温还是在衰减 | "一直很热但已到平台期"会算成 0 增速，被误判为没价值 |
   | **B. `momentumRatio`（爆发动能）** | 最近**短窗**（窗口的 1/8，至少 1 小时）的速率 ÷ **整窗平均基线** | 现在**是不是正在爆** | 早期小样本抖动会被误判成爆发 |

   判定：`growth > 5%` 记 `growing`、`> 20%` 记 `rising`；**两个口径同时成立（`growth > 20%` 且 `momentumRatio > 1.5`）才标记 `surging`（正在起爆）**。
   另外输出近 1/4 窗口每小时互动量 `velocity`、近 1/4 窗口发帖占比 `freshness`、逐时分布（前端画迷你走势图）与**峰值时间**（用于算检测时效）。

   > 实测有效：24H 窗口中「AI capex」环比 **−50%** 但短窗动能 **+33%** → 被正确判定为"非起爆"（它是窗口早期爆过、现已退潮）；而「US CPI」，环比 **+167%** 且动能 **2.18x** → 判定"正在起爆"。单一指标做不到这个区分。
6. **AI 摘要**：给出"N 个账号讨论 M 条帖子、互动量、环比 +X%、市场共识、主要分歧、高频标的、多空结构"的一段中文摘要——即"核心讨论内容"的总结。
7. 每条话题都会带**证据链**：最相关的原始帖子 + 参与账号列表（题目要求的"展示相关 Posts 和 Accounts 作为依据"）。

> 生产版可把第 2 步换成 embedding 聚类（同一份接口），但对 MVP 而言，可解释的规则聚类更好——面试时每一步都能讲清楚"为什么它算热点"。

## 6. 机会排序逻辑（Opportunity Ranking Logic）

题目原话：**"讨论多"并不意味着"最值得 TelyClaw 跟进"**。所以分数不是热度，而是"机会值"。

```
Opportunity Score (0-100) = 100 × Σ ( 因子归一值ᵢ × 权重ᵢ / Σ权重 )
```

| 因子 | 默认权重 | 原始值 | 为什么它进公式 |
|---|---|---|---|
| `momentum` **爆发动能** | 0.18 | 最近短窗速率 ÷ 整窗平均基线 | 区分"**一直很热**"和"**刚刚起爆**"——前者已经没有先手优势，后者才是增长岗真正要抓的窗口 |
| `velocity` 热度增速 | 0.22 | 近 1/4 窗口每小时互动量 | 热点是**现在**快，不是过去多 |
| `engagement` 互动规模 | 0.16 | 窗口内总互动（赞+2×转+3×评+2×引） | 决定可能的曝光天花板 |
| `accounts` 参与账号数 | 0.12 | 独立账号数 | 单账号刷屏不是趋势；多来源共识才是 |
| `freshness` 时效性 | 0.08 | 近 1/4 窗口发帖占比 | 区分"正在发生"和"已经过去" |
| `relevance` TelyClaw 相关性 | 0.14 | 命中产品/受众关键词的帖子占比 | **是不是我们该说的**（否则接了也接不住） |
| `contentOpportunity` 内容可生产性 | 0.10 | 数字密度 42% + 账号多样性 28% + 多空分歧 30% | 有数据能拆解、有分歧能表态，才写得出有信息量且有点击的内容 |

> 为什么把 `momentum` 独立成一个因子、而不是并进 `velocity`？
> 因为两者量纲不同、回答的问题也不同：`velocity` 是"绝对热度有多快"，`momentum` 是"相对它自己的基线在放大多少倍"。
> 一个话题可以绝对热度很高（大账号发一条就够）但完全没有起爆动能；也可以绝对热度不高但 3 小时内翻了 3 倍。
> **增长岗要抓的是后者**——前者你抢不到先手，后者才是内容能吃到流量的窗口。归一化后加权，让两种机会都能被正确排序。

设计说明：
- 因子先做 **min-max 归一**（同一批话题内相对比较），再加权求和，所以"满分 100"是相对概念，跨批次不可直接比较。
- 权重可在 **设置** 页实时调整并立刻重算 —— 这就是"自己定义机会分数"的落点：我把它做成可调参数，而不是藏在代码里的魔法数。
- 每个话题都输出 **逐因子拆解（因子分 / 权重 / 贡献分 / 原始值）** 和中文理由列表，以及 1 段 **Top1 结论**（领先第二名多少分、建议从哪个角度切入）。
- 每个话题还会输出一条 **`timingAdvice` 时效建议**，把双口径的结论直接翻译成动作：`立即动手（2 小时内）` / `优先处理（6 小时内）` / `正常排期` / `不着急（热度已退潮）`。
  —— 分数的意义不在于排名，而在于**告诉人现在该不该动手**。

## 7. 排期监控与机会提醒（Scheduled Monitoring · Bonus 项）

**要解决的问题**：热点窗口期只有几小时，人不可能一直盯着屏幕。所以系统必须能**无人值守地轮询**，而且**只在真的出现高分机会时才打扰人**。

```
定时器（可配置间隔）
   └→ runFull()  ← 与"手动点按钮"共用同一个 pipeline，保证自动/手动口径完全一致
        └→ 抓取 → 热点识别 → 机会排序
             └→ 机会筛选（阈值 / 去重 / 静默时段）→ 提醒队列 → 概览页提醒面板 + 未读角标
```

**三个都不是随手写的设计**：

| 设计 | 为什么必须有 |
|---|---|
| **去重（dedupe）** | 同一话题在 N 小时内只提醒一次。否则 30 分钟一轮，同一个热点会把你轰炸 20 次——**提醒一旦泛滥，就等于没有提醒**。 |
| **静默时段 + 破例阈值** | 夜间不打扰；但如果分数高到破例阈值（真爆点），**仍然穿透静默**。原则是"重要的不是不打扰，而是不漏掉真正重要的那一条"。 |
| **提醒自带行动建议** | 每条提醒直接带上时效建议（立即动手 / 优先处理 / 正常排期）+ 一个"为该热点生成内容"的按钮，点开就能干活，而不是只看个分数。 |

**可配置项**（设置页修改，保存后立即重启定时器生效）：轮询间隔、每轮时间窗口、提醒分数阈值、去重窗口、静默时段起止、静默破例阈值。
**接口**：`GET /api/scheduler`、`POST /api/scheduler`、`POST /api/scheduler/tick`（立即执行一轮，便于演示时不用等轮询周期）。

> 实现文件：`src/scheduler.js`（定时器、去重、静默判定）+ `src/pipeline.js`（共用的抓取→识别→排序链路）。
> 默认**关闭**，避免未经同意就持续消耗资源；在概览页勾选"启用定时轮询"即可打开。

## 8. 内容生成逻辑（Content Generation Logic)

**输入**：一个热点话题（含摘要、情绪结构、事实数字、标的、样本帖）
**输出**：3 个角度各 1 条，其中至少 1 条标记为"可直接发布"

| 角度 | 定位 | 结构 |
|---|---|---|
| Hot Take / Opinion | 表态、引发讨论 | 反共识断言 → 用数据支撑（帖子数/账号数/环比）→ 留一个观察点 |
| Educational / Insight | 给读者可带走的东西 | 3 个常见误解 / 4 行速览（发生了什么 → 为什么重要 → 看什么 → 忽略什么） |
| TelyClaw Product Angle | 自然接到产品叙事 | 从这次热点里"时间窗口有多短"过渡到"检测→发布的流程问题"，而不是硬广 |

**两种实现，同一套校验**：
- `LLM_MODE=mock`（默认）：内置确定性生成器，用"骨架 + 话题事实"填充（事实块来自 `extractFacts`：帖子数、账号数、环比、数字、标的、人话短语）。好处是不联网也能产出合格文案，demo 不会因为 API 失败而断。
- `LLM_MODE=openai`：走任意 OpenAI 兼容 `/chat/completions`，Prompt 里明确给出产品定位、受众、文风，并**硬性要求"禁止出现源帖中的完整句子"**，返回严格 JSON。失败自动回退到 mock（并在 UI 提示）。

**原创度校验（强制，不通过不许发布）** —— 直接回应题目"内容不能只是 Copy、Rewrite 或 Summary 原始 Tweet"：
1. 与所有样本源帖计算**加权 Jaccard 语义相似度**，≥ 0.45 判为涉嫌 Rewrite；
2. 计算**连续 5 词重叠率**，≥ 0.20 判为涉嫌 Copy；
3. 字符数 ≤ 280、长度下限 60 字符；
4. 输出 `原创度% = (1 - max(相似度, 2×重叠率)) × 100`，在 UI 上逐条展示；任一不通过 → 状态变 `needs_revision`，**批准按钮与发布接口都会拒绝**（服务端也会二次校验，不只靠前端）。

**第二道视角：编辑 Agent 自评（Editor Agent）**

生成完不是就完了。"写"和"审"是两种不同的能力，让同一个环节既写又判，就会自己给自己打高分。所以生成之后**再加一个独立的编辑 Agent** 做评审：

| 维度 | 权重 | 看什么 |
|---|---|---|
| `hook` 开头钩子 | 0.22 | 第一句能不能让人停下来（开头就说"我们要说…"是最弱的钩子，会扣分） |
| `specificity` 具体性 | 0.20 | 有没有可验证的数字、有没有相关标的 |
| `originality` 原创度 | 0.24 | 直接取硬校验（相似度 / 5 词重叠）的结果，不做二次判断 |
| `audienceFit` 受众匹配 | 0.18 | 是不是说给 TelyClaw 的 ICP 听 |
| `clarity` 表达清晰度 | 0.16 | 可读性与结构（分行、编号、句长） |

输出：加权总分（0–100）、结论（`可发布` / `建议润色` / `建议重写`）、以及**最多 4 条可执行的修改建议**——要求是"说清改哪一句、往哪个方向改"，而不是"可以更好"这种废话。

- `LLM_MODE=mock` 时用确定性启发式规则（`heuristicReview`），离线可用；`openai` 时走真实评审 Prompt（`llmEditorReview`），失败自动回退。
- **它不是硬闸门**：真正的硬闸门只有原创度校验。编辑 Agent 的结论是"提示"，用来把人从"读一遍找毛病"里解放出来——判断权仍在人手里。
- 人工改完可以点 **「编辑 Agent 复评」** 重跑一次，形成 `生成 → 自评 → 人改 → 复评 → 批准` 的小闭环。

**预估表现（模拟）**：`曝光 = (velocity×1.6 + engagement/18 + 400) × 角度系数 × (1 + 分歧度×0.3)`，互动按 1.6%–3% 转化，再乘 ICP 匹配度得到"合格互动"。这是用于验证指标口径的启发式模型，UI 与本文档都明确标注为模拟值。

## 9. 人工审核闭环（Human-in-the-loop）

```
Trend → AI Draft → Editor Agent 自评 → Human Edit → Reviewer 批准 → Publisher 发布
```

- 草稿状态机：`draft → (人工编辑) → approved → published`，另有 `rejected`（驳回）与 `needs_revision`（未过校验）。
- 每次编辑都重新跑原创度校验，并在 `history` 里留痕（**谁**、什么时候、做了什么动作、原创度多少）。

### 9.1 角色分离与权限（作者 / 审核人 / 发布人）

一个人写、一个人批、一个人发——这是内容团队的真实形态。所以角色是独立的一层，而不是"谁点都行"：

| 角色 | 能做的事 | 刻意**不能**做的事 |
|---|---|---|
| `editor` 内容编辑 | 生成内容、编辑文本、分配审核人 | ❌ 不能批准（避免"自己写自己批"） |
| `reviewer` 审核人 | 编辑、批准、驳回、分配审核人 | ❌ 不能发布（避免"批完直接发"绕过发布人） |
| `publisher` 发布人 | 发布已批准的草稿 | ❌ 不能编辑、不能自己批准（避免"自己批自己发"） |
| `admin` 管理员 | 全部 | — |

**关键点：权限在服务端强制执行，不是前端把按钮变灰。** 直接 `curl` 打接口一样会被拦：

```bash
# 用「内容编辑」身份批准 → 403
{"error":"当前身份「Alice（内容编辑）」没有「批准」权限；需要角色：审核人 / 管理员。可在右上角切换身份。"}
# 用「发布人」身份发布未批准的草稿 → 400
{"error":"发布前必须先由审核人批准（当前状态：draft）。这是刻意的流程约束：作者 / 审核人 / 发布人分离。"}
```

- 发布走**双闸门**：`质量校验通过` + `状态为已批准`，两条都满足才放行；发布记录里会同时记下**审核人**和**发布人**。
- 草稿支持**分配审核人**（`assignedTo`），对应真实团队的"任务指派"。
- 前端右上角可切换"当前身份"，按钮会按权限自动禁用并给出原因提示——**禁用只是提示，拦不住人的地方由服务端兜底**。
- MVP 的发布仍是**模拟发布**（生成占位 URL）；真实 X 写入 API 属于 Bonus 项，未做（见 §11）。

## 10. 指标口径（Metrics）

**North Star Metric：Qualified Engagement Generated from Trends**
= Σ(由热点内容带来的互动 × ICP 匹配度)。用"合格互动"而不是"曝光/互动总量"，是因为增长岗真正要对齐的是**受众质量**：TelyClaw 的 ICP 是 AI-native 创业者/开发者/量化与研究者/财经与 AI 内容创作者。

| 支撑指标 | 口径 | 为什么重要 |
|---|---|---|
| 话题发现延迟 | 话题首帖 → 被系统首次检测到 | 监控能不能跟上新闻节奏 |
| 峰值提前发现率 | 首次检测时间早于话题峰值的话题占比 | 追热点的本质是抢时间窗 |
| 内容产出量 | 草稿总数（按状态拆分） | 产能 |
| 审核通过率 | 通过 / 已审核草稿 | AI 草稿的可用度（越高越省人力） |
| 热点命中率 | 发布后话题仍在升温的占比 | 避免追"已经死了的热点" |
| 互动提升 | 已发布内容预估互动 / 全量草稿均值 − 1 | 排序逻辑是否真的选得更好 |
| 闭环漏斗 | 热点 → 草稿 → 批准 → 发布 | 定位流失环节 |

**⚠️ 诚实声明（重要，也是题目"说明当前 MVP 局限"的一部分）**：
- 数据源是仿真数据时，上述指标是**基于仿真数据的估算**，用于验证口径与闭环是否成立，不代表真实 X 表现（UI 上也常驻提示）。
- 时效类指标在当前环境里天然为负/为 0：仿真数据是"上线那一刻回填过去 7 天"，系统首次检测时间 = 你点按钮的时间，所以「峰值提前发现」必然显示为负。它衡量的是**持续监控时能提前多久发现话题**，切到真实 API 连续采集后才有正数意义。

| POST | `/api/draft/status` | 批准 / 驳回（需 `reviewer` 或 `admin` 角色） |
| POST | `/api/draft/publish` | 发布（需 `publisher` 或 `admin`，且状态必须为已批准） |
| POST | `/api/draft/assign` | 分配审核人（需 `assign` 权限） |
| POST | `/api/members/actor` | 切换当前操作身份（演示用，生产应由登录态决定） |
| GET / POST | `/api/scheduler` | 读取 / 修改排期监控配置（修改后立即重启定时器） |
| POST | `/api/scheduler/tick` | 立即执行一轮轮询（便于演示，不用等周期） |
| POST | `/api/alerts/read` `/api/alerts/clear` | 提醒标记已读 / 清空 |
| GET | `/api/metrics` | 北星指标与支撑指标 |
| POST | `/api/config` | 切换数据源 / 生成模式 / 调整评分权重 |

> 涉及权限的接口在服务端做角色校验：无权限返回 **403**，发布未批准的草稿返回 **400**。
> 想自己验证权限是否真的生效，可以直接 `curl` 打这些接口——前端的按钮禁用只是提示。

## 17. 与现有开源方案的对比与取舍（Borrowed / Differentiated）

在动手之前我去 GitHub 上找过同类项目，结论是：**没有"现成的 TelyClaw"可以抄，但每个环节都有工业级答案可以参考**。
（搜 `twitter trend detection content generation` / `social listening trend monitoring` 命中的都是 0–1 star 的新仓库，其中 4 个最接近的仓库 README 还是同一份 AI 模板批量生成的，不能作为参考。）

### 17.1 借鉴了什么

| 环节 | 参考项目 | 借鉴的点 | 本项目落地 |
|---|---|---|---|
| 数据采集 | `vladkens/twscrape` ★2.9k | 账号池 + 会话持久化 + **限流自动换账号** + 每账号独立代理 | 写进 §4 阶段 0（冷启动方案），并在 §4 明确标注 ToS 灰色地带 |
| 数据采集 | `DIYgod/RSSHub` ★46.5k | 把任意站点变成 RSS 的统一聚合层 | 用作 §4 降级链里的"第三方聚合源" |
| 热点识别 | `MaartenGr/BERTopic` ★7.9k | ① **Guided Topic Modeling**（用种子词表引导聚类）② **Online/Incremental**（增量更新）③ **c-TF-IDF** 给簇生成主题词 | ① 本项目的 `TOPIC_SEEDS`+`ANCHORS` 正是"引导式"思路，可平滑替换为该库 ② 与排期监控结合做增量更新（下一步）③ 本项目的 **IDF 加权自动命名**与之同源 |
| 内容生成 | `crewAIInc/crewAI` ★59.6k | 多角色分工：写手只写、**编辑专门挑毛病** | 落地为 **编辑 Agent 自评**（§8）：把"写"和"审"拆成两个环节，避免自己给自己打高分 |
| 审核与发布 | `gitroomhq/postiz-app` ★37.1k / `inovector/mixpost` ★3.8k | **工作区 + 角色权限 + 任务指派**的团队协作模型 | 落地为 **作者/审核人/发布人分离 + 服务端强制校验**（§9.1） |
| 审核与发布 | `langchain-ai/langgraph` ★43.2k | **human-in-the-loop** 中断/恢复的状态机表达 | 本项目用轻量状态机实现同一语义（草稿 → 已批准 → 已发布 + 留痕） |

### 17.2 刻意**不**借鉴、以及为什么

| 没有采用 | 原因 |
|---|---|
| 直接引入 `CrewAI` / `LangGraph` 做 Agent 编排 | 面试场景要把每一步讲清楚。手写状态机 + 显式函数调用，比藏在框架里的执行图**更能说明"我知道原理"**；而且零依赖让评审 clone 下来就能跑。 |
| 直接引入 `BERTopic`（embedding + UMAP + HDBSCAN） | 需要下载模型与额外依赖，且黑盒聚类在面试时讲不清"为什么它算热点"。本项目用**可解释的规则聚类**，并在 README 里明确写出"生产版换 embedding（同一接口）"的升级路径。 |
| 用 `n8n` / `Dify` 拼一条可视化工作流 | 30 分钟确实能拼出 demo，但**这道题考的是判断力不是连线能力**：Opportunity Score 的 7 个因子、原创度校验的阈值口径，藏在工作流节点里是讲不出来的。 |
| 引入 `twscrape` 直接抓真实数据 | ToS 灰色 + 稳定性不足，不适合作为交付物；把它写进"冷启动方案"更诚实，也更有工程判断。 |

### 17.3 本项目在开源生态里属于**空白**的部分（也就是真正的差异化）

翻遍同类项目后有两件事**在那些几万 star 的项目里都不是默认能力**：

1. **可解释的 Opportunity Score** —— "讨论多 ≠ 值得跟进"这个判断，以及 7 个因子的拆解、权重可实时调整、逐条中文理由 + 时效建议。开源社媒工具普遍只做到"按互动量排序"。
2. **强制原创度校验** —— 语义相似度 ≥45% 判涉嫌 Rewrite、连续 5 词重叠 ≥20% 判涉嫌 Copy，**服务端拒绝批准和发布**。这是直接回应题目"内容不能只是 Copy / Rewrite / Summary"的要求，也是同类项目普遍缺失的一环。

> 一句话：**没有现成的可以抄，但每个环节都有工业级答案可以参考**；把"参考了什么、为什么不全盘照搬、哪两块是自己独有的"讲清楚，比多写 1000 行代码更有说服力。
